# 项目分块管理

> 把项目拆成 7 个可独立推进、可独立验收的块，便于单人分块管理。
> 完成度是**工程判断**，不是精确度量；每次推进请更新本表。
>
> 状态图例：✅ 已完成 · ⚠️ 部分完成 · ❌ 未开始

## 0. 总览

| 块 | 职责（一句话） | 状态 | 表 | 端点 |
| --- | --- | --- | ---: | ---: |
| **A. 账号与合规** | 谁能用、数据怎么删 | ✅ 100% | 7 | 13 |

| **E. 定制与导出** | 针对某岗位产出可投递的简历 | ⚠️ 25% | 3 | 9 |

## A. 账号与合规 ✅ 100%

**职责**：用户身份、会话安全、数据生命周期。

- **表**：`users`、`invitations`、`sessions`、`auth_rate_limits`、`email_verification_tokens`、`password_reset_tokens`、`account_deletion_requests`
- **端点**：`auth/*`（11）+ `health/*`（2）
- **已交付**：邀请码注册、邮箱验证、找回密码（QQ SMTP，令牌放 URL 片段）、CSRF、登录限流、会话轮换与撤销、账号删除 7 天窗口
- **卡点**：无
- **验证**：`pytest` 的 `test_auth.py` / `test_account_deletion.py` / `test_health.py`
- **本块不需要再投入。**

---

## B. 简历事实库 ⚠️ 55%

**职责**：PDF/DOCX/文本 → 区段 → 事实 → 用户逐条确认 → 可溯源的事实库。

- **表**：`resume_profiles`、`resume_facts`
- **端点**：`resumes/*`（import / list / get / facts·PATCH / confirm）
- **已交付**：三种格式导入、临时文件即删、区段切分（中文标题字典）、技能抽取、逐条确认闭环、`source_text` + `source_location` + `confidence` + `created_by` 溯源字段
- **缺口**：
  1. 🔴 **版面解析未做**：`page.get_text("text")` 丢掉了字号/加粗/坐标；DOCX 丢掉了 `style.name`。这是全项目最高杠杆的缺口
  2. 🔴 **"优势/亮点"概念不存在**：`fact_type` 只有 `section` / `skill`
  3. 🟠 区段字典只有 13 个标题，"实习经历""校园经历""荣誉奖项"落进 `other`
- **前置**：优点 1、3 是纯规则，不需要 G；优点 2 需要 G
- **验证**：`test_resume_import.py` + 新增版面解析单测
- **交付物**：一份"每条都能回到原文"的事实库

## C. 岗位库 ⚠️ 30%

**职责**：把 JD 变成结构化、分类别、可检索的岗位数据。

- **表**：`job_descriptions`、`job_requirements`、`skill_aliases`
- **端点**：`jobs/*`（from-text / list / get）
- **已交付**：JD 粘贴、**分节分句要求抽取**、必需/加分判定、202 项分类技能词典、`skill_aliases` 数据表（可增量演进）
- **缺口**：
  1. 🔴 **只抽技能类要求**：`parse_job_requirements` 只在命中技能词时才产出要求 → "3 年经验""本科以上"被**直接丢弃**
  2. 🔴 **无城市/公司/薪资字段** → 需求②的"按城市"没有数据基础
  3. 🟠 `job_watch` 是**独立脚本**，不在产品里（无 API、无页面、无表）
  4. 🟠 来源仅 9 所高校就业网 + 国资委，**8 个月累计仅 1 条岗位**
- **前置**：缺口 1 需要扩展领域模型（`TechnologyRequirementValue` → 判别联合），缺口 2 需要迁移
- **验证**：`test_job_matching.py` + 新增分类别抽取测试

## D. 匹配引擎 ⚠️ 50%

**职责**：已确认事实 × 岗位要求 → 可解释、可版本化的匹配结论。

- **表**：`job_matches`
- **端点**：`POST /matches`、`GET /jobs/{id}/matches`
- **已交付**：`satisfied` / `no_evidence` 两组逐项证据；绑定「简历 + JD + 算法版本」三元唯一约束的**不可变快照**；只用已确认事实
- **缺口**：
  1. 🔴 **只有精确名称匹配**，无语义召回（"熟悉 K8s" 匹配不到 "Kubernetes 容器编排"——虽然词典别名能覆盖一部分）
  2. 🟠 不输出任何排序/匹配度（有意为之，规则禁止单一匹配分）
- **前置**：语义召回需要 G（Embedding）
- **验证**：`test_job_matching.py`
- **交付物**：能拿给用户看的"为什么匹配/为什么不匹配"

## E. 定制与导出 ⚠️ 25%

**职责**：针对一个具体 JD，产出可投递的简历版本。

- **表**：`optimization_suggestions`、`resume_versions`、`document_exports`
- **端点**：`optimizations/*`（4）+ `resume-versions/*`（3）+ `exports/*`（2）
- **已交付**：建议生成、逐条 accept/reject、**幂等**版本快照、中文 ATS 友好 DOCX、导出 24 小时清理
- **缺口**：
  1. 🔴 **改写本身为零**：`optimization_service.py` 里 `original_text == proposed_text`，唯一动作是把技能区段前置。**简历字数不变、关键词不增，机筛命中率几乎不会变**
  2. 🔴 无 ATS 关键词覆盖率分析
  3. 🟠 PDF 导出未实现
  4. 🟠 **审批负担未解决**：规则要求逐条点击，50 岗 × 20 条 = 1000 次点击，真实使用会直接失效
- **前置**：缺口 1、2 需要 G；缺口 4 需要**规则变更**
- **验证**：`test_optimizations.py` / `test_resume_versions.py` / `test_document_exports.py`

## G. 模型层与事实守卫 🟡 70%

**职责**：让 B/C/D/E 能用模型，同时保证模型不撒谎。**横向能力，被多个块依赖。**

- **表**：`agent_runs`、`agent_checkpoints`（任务状态机已建）
- **端点**：`agent-runs/*`（3）
- **已交付**：
  - 可恢复 Agent 状态机、持久化审批检查点、`FOR UPDATE SKIP LOCKED` 任务队列
  - ✅ **`LLMProvider` 适配层**（`domain/llm.py` + `infrastructure/llm_provider.py`）：
    provider port、Null provider（默认拒绝作答）、OpenAI 兼容 HTTP 适配器（客户端可注入）、
    超时与 HTTP 错误分类、`ScriptedLlmProvider` 供测试
  - ✅ **事实守卫**（`domain/fact_guard.py`）：模型输出必须附带**原文逐字引用**，
    引用对不上即丢弃；**刻意忽略模型自报置信度**（幻觉往往更自信）；
    标点归一化投影比对（解决 PDF 全角标点），存储保留原文；类别白名单；去重
  - ✅ **陈述接地校验**：**仅有真实引用还不够** —— 语句本身不得超出引用的支撑范围：
    语句里的任何数字/时长必须在引用中出现，且宣称的熟练度不得高于引用
    （`了解 < 熟悉 < 熟练 < 精通`）。这条拦住了"引用真实、陈述夸大"的伪造
  - ✅ **LLM 锚定抽取服务**：确定性词典先行兜底，模型输出**增量且必须过守卫**；
    provider 故障/超时/未配置一律**降级到确定性路径**，导入流程不中断
  - ✅ **已接入导入接口**：`POST /resumes/import` 在确定性事实之后追加模型事实，
    逐行记录 `created_by`（`deterministic_parser` / 模型名）与置信度分层，
    `source_location` 一律取自守卫解析出的真实位置，**不采信模型自报的位置**
  - ✅ **ReAct 工具调用循环**（`domain/react_agent.py` + `application/agent_tools.py`）：
    模型自主选工具、观测回灌为上下文（记忆）、步数上限、工具异常与格式错误降级为观测；
    三个真实工具（技能词典查询 / 原文定位 / 词典规模）
  - ✅ `cli.py guard-report`：**不依赖数据库**，直接对模型输出跑守卫并报接受率
- **缺口**：
  1. 🔴 **`EmbeddingProvider` 不存在**（向量语义召回，见二期方案）
  2. 🟡 改写前后的 `A ⊆ B` 集合断言**尚未接入 E 块**（守卫目前只覆盖抽取阶段）
  3. 🟡 用量计费与 Prompt 版本号（`PROJECT_RULES.md` 546–573 行要求）未落库
- **验证**：✅ 56 个新单测（`test_fact_guard.py` 20 + `test_llm_provider.py` 12 +
  `test_react_agent.py` 18 + `test_llm_import_integration.py` 6）；全套 **109 passed**；
  `guard-report` 实测一次混合样本 **接受 3 条、丢弃 3 条**（虚构技能 / 虚构指标 / 非法类别）；
  集成测试覆盖"幻觉引用不入库""provider 抛错不中断导入""模型事实是增量而非替换"；
  **并对自己发起过攻击测试**，据此发现并修复了"真实引用 + 夸大陈述"这个漏洞（见下）
- **本块的每个子项都可以独立验收。**

## 与三条需求的映射

| 用户需求 | 涉及块 | 说明 |
| --- | --- | --- |
| ① embedding 切分、摘优势技能 | **B + G** | 切分在 B（版面解析），优势抽取要 G；技能抽取已提升 |
| ② 按岗位+城市爬取、生成链接投递 | **C + F** | 城市字段在 C，"投递"在 F（且需规则变更） |
| ③ 按 JD 润色过机筛 | **D + E + G** | 匹配在 D，改写与覆盖度在 E，能力来自 G |

## 建议的推进顺序

| 顺序 | 块 | 为什么排这里 | 需要模型/密钥 |
| ---: | --- | --- | --- |
| 1 | **B（版面解析）** | 最高杠杆，纯规则，决定后面一切的质量 | ❌ |
| 2 | **C（要求分类别）** | 纯数据/规则，让"经验/学历"要求不再被丢弃 | ❌ |
| 3 | **G-1（LLMProvider）** | 需求①③的共同前提；规则已写好，照做 | ✅ **已完成** |
| 4 | **G-2（事实守卫）** | **必须先于**任何生成功能，否则无法信任改写 | ✅ **已完成**（抽取阶段） |
| 5 | **B（优势抽取）** | 依赖 G-1 | ✅ |
| 6 | **D + G-3（Embedding 召回）** | 提升召回率 | ✅ |
| 7 | **E（真改写 + 覆盖率）** | 需求③主体，依赖 G-1/G-2 | ✅ |
| 8 | **F（投递追踪）** | 需先完成规则决策 | ❌ |

**1–2 步现在就能做，不需要任何密钥。**

## 维护约定

- 每完成一块的某个子项，更新本文件的状态与缺口清单
- 任何**规则变更**先更新 `docs/RULE_CHANGE_PROPOSAL.md`，确认后再改 `PROJECT_RULES.md` 与 `docs/DECISIONS.md`
- 新增数据表 / 端点时同步更新第 0 节的总览表
- 缺口项前用 🔴（阻塞）／🟠（重要非阻塞）标注优先级
