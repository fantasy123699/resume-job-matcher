## 项目名称

**履历校准台**（Resume Calibration Desk）

**一句话定位**：把简历变成可验证的结构化事实库，再与目标岗位 JD 做可解释的逐项匹配，
只优化表达、绝不捏造事实。

**个人角色**：独立设计并实现全部前后端、数据库、部署与工程规范（含 42KB 工程规则文档与 ADR 决策记录）。

## STAR 项目介绍

### S — 背景

中国大陆程序员求职者海投时有三个真实痛点：简历与目标岗位 JD 的关键词不匹配，在 ATS 机筛阶段就被淘汰；为提高过筛率而夸大经历，进入面试后因细节追问被拆穿；投递量大，简历版本混乱、无法追踪哪份简历投了哪家公司。

### T — 目标

设计并实现一个 Web 工具，让求职者把简历沉淀为**可验证的结构化事实库**，与目标 JD 完成**可解释的逐项匹配**，并生成**不改变任何事实**的优化建议与 ATS 友好导出。

核心约束：**系统只能优化表达、顺序与格式，不得新增经历、技能或数据；所有结论必须可回溯到原文。**

### A — 我做的事

**全栈架构**

- 单仓库三进程：Next.js + TypeScript（Web）、FastAPI + Pydantic（API）、Python Worker（异步任务），PostgreSQL 作为唯一持久化，Docker Compose + Caddy 部署。
- 18 张数据表、12 个 Alembic 迁移、35 个 REST 端点；全部接口用 Pydantic Schema 强约束，禁止直接返回 ORM 对象。
- 前端 10 个页面、8 个组件，覆盖注册 → 事实确认 → JD 匹配 → 建议审批 → 版本导出全流程，每个页面都含加载/失败/恢复状态。

**事实溯源（核心数据设计）**

- 每条抽取事实持久化 `source_text`（原文片段）+ `source_location`（页/行/表格单元格坐标）+ `confidence` + `created_by`，让任何匹配结论都能回到简历原文。
- 匹配结果输出 `satisfied` / `no_evidence` 两组逐项证据；未找到证据的要求显式标记「当前无证据」，不输出录用概率——**不做无法验证的承诺**。

**不可变版本与幂等**

- 匹配快照绑定「简历版本 + JD + 算法版本」三元唯一约束，更新主简历不会改写历史结论。
- 版本生成使用幂等键，同一用户重复提交同一键返回同一版本；并发下用唯一约束 + 捕获 `IntegrityError` 兜底。

**无 Redis 的并发任务队列**

- 在「不引入 Redis / 消息队列」的成本约束下，用 PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED` 实现并发安全的任务领取。
- 实现可恢复 Agent 状态机：任务状态与**人工审批检查点持久化**，API/Worker 重启后任务可恢复，不会静默丢失。

**JD 解析引擎（规则，分节 + 分句）**

- 抽取技术要求与加分项，并记录原文位置。实现**分节状态机**：章节标题独占一行时（`加分项` 换行后接要求列表），后续条目继承该章节的必需/加分属性；**按分句**判定，使同一行内的必需项与加分项互不污染；福利章节不产生要求。
- 实测修复了一个真实缺陷：原实现按整行匹配 4 个加分关键词，导致「加分项」独占一行时后续要求被误判为必需。

**技能词典（从代码搬进数据）**

- 把硬编码的 26 项技术别名表升级为 **202 项规范技能 / 413 条别名 / 12 个类别**的词典，用**单个编译后的正则**匹配，替代原先「每个技能一次 `re.search`」，匹配成本不随词典规模增长。
- 用词边界杜绝 `Java` 误配 `JavaScript`、最长优先杜绝 `Spring` 抢占 `Spring Boot`；对 `Go` 这类兼作英文单词的别名加了后续小写词否定前瞻，避免把 `Go to market` 识别成 Go 语言。
- 新增 `skill_aliases` 表承载运维新增词条，**词典可在不改代码、不重新部署的前提下增量演进**；采用并集合并而非覆盖，保证种子词表的改进始终生效。

**安全与合规工程**

- 邀请码注册、邮箱验证与找回密码（一次性令牌放 URL 片段，避免进入访问日志）、CSRF 防护、登录限流、会话轮换与撤销。
- 数据生命周期：原始上传文件只写系统临时目录、解析后立即删除；导出文件 24 小时自动清理（创建时清理 + Worker 定时清理双保险）；账号删除立即冻结、7 天后清除活跃数据。
- 公开岗位采集脚本：仅采集已登记、无需登录的政府与高校官方招聘页，遵守 robots、域名白名单、超时与重试上限，**不登录招聘平台、不绕过访问控制**。

### R — 结果

- 独立完成 18 张表、12 个迁移、35 个 REST 端点、16 个测试模块，打通注册到导出的完整业务闭环。
- 工程基线（**已实测**）：`pytest` **109 passed**（对真实 PostgreSQL 17）、`ruff`（全通过）、`mypy`（45 源文件，仅剩 `fitz` stub 提示）、`eslint`、`tsc`、`vitest` 全部通过；12 个数据库迁移全部应用成功。
- **接入 LLM 后补上了事实守卫**：先实现 provider port（不依赖厂商 SDK）与锚定抽取，再对**自己的守卫发起攻击测试**，发现"引用真实但陈述夸大"可绕过（如引用「了解 Docker」而陈述「精通 Docker」），据此补上陈述接地校验；修复前先验证未误杀正常用例（标点差异、子串引用、原文真含数字等 9 例全部通过）。
- 沉淀 42KB 工程规则文档与 ADR 决策记录，把「不捏造事实」从口号落成可执行的代码约束与数据字段。
- **准备期间跑通全量测试，发现并修复两个真实缺陷**：① 爬虫的发布日期提取在有截止时间时取到了截止日期（`max` 聚合的副作用），改为优先取「发布/更新时间」标记后的日期、无标记时回退原行为；② 一个依赖真实时钟的测试未固定 `now=`，数据超过 `max_age_days` 后必然失败。

## 面试可以展开讲的技术取舍

1. **为什么每条事实都存 `source_location`** —— 在模型会幻觉的前提下，可追溯性要建在数据结构层，而不是靠 prompt 约束。这也是后续接 LLM 时事实守卫的基础。
2. **为什么匹配快照要绑「算法版本」** —— 换解析器或词典后必须能识别哪些历史结论已失效，而不是静默复用旧结果。
3. **为什么不用 Redis** —— 单机 2 核 4 GB 起步的成本约束下，`FOR UPDATE SKIP LOCKED` 已满足并发安全，不引入没有实际需求的基础设施。
4. **为什么技能词典要并集而非覆盖** —— 用迁移种子入表会造成「DB 旧值遮蔽代码新值」的维护陷阱，并集合并让种子改进始终生效，同时保留运维增词能力。
5. **精确率优先于召回率** —— `Java`/`JavaScript`、`Go`/英文单词这类混淆一旦误判，会直接产出错误结论；宁可漏，不可错，漏的交给用户逐条确认兜底。
6. **为什么保留「逐条人工确认」** —— 简历是开放域，任何封闭抽取方案都会漏。用确认机制兜底不是妥协，是处理开放域的正确架构。
7. **怎么发现那两个 bug 的** —— 数据库一直跑不起来，全量测试从未执行过；我把 PostgreSQL 跑起来后第一次跑出真实结果，就暴露了两个缺陷。**能讲的故事是"我意识到测试从没真正跑过，于是先补验证再谈功能"**，而不是"我写了多少功能"。
8. **一个我主动识别并承认的设计矛盾** —— 现行规则要求每条修改建议逐条审批，而 `create_resume_version` 把它做成了硬约束（有一条 `pending` 就抛错）。这意味着一旦实现真正的改写（每岗 10–30 条建议），海投 50 个岗位就需要约 1000 次点击，**功能做得越好，产品越不可用**。我的结论是这必须先改规则、而不是改代码，并列出了审批分层的方案。**讲这个比讲功能更能体现判断力。**

## 二期技术方案（尚未实现，按设计口径写）

- **中文简历版面解析**：用 PyMuPDF `get_text("dict")` 取字号、加粗标记与坐标，识别标题层级、双栏排版与页眉页脚；DOCX 侧读取段落样式名与大纲级别，替代当前纯文本行扫描。
- **混合匹配架构**：确定性词典与句式规则保证精度与可解释性（作匹配证据），向量语义召回保证召回率（仅标记「疑似匹配」并交用户确认），两者取并集但标注来源与置信度分层。
- **词典语料驱动演进**：从 JD 语料用句式模板、中文新词发现（互信息 + 左右邻接熵）与向量聚类持续挖掘新术语，人工审核后入库。
- **LLM 锚定抽取与事实守卫**：模型每条输出必须能锚定回原文位置，锚定失败即丢弃；改写前后对实体与数字集合做包含断言，用确定性校验而非模型自检防止捏造。
- **ATS 关键词覆盖率分析**：输出目标 JD 要求词在简历中的覆盖情况与缺口清单。
- **岗位召回与投递追踪**：为 JD 增加城市等结构化字段，扩充已登记的公开来源，产出按匹配度排序的岗位清单与投递追踪表。
